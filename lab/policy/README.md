# `lab/policy` — the SIGSTOP harness

What a real FreeRADIUS does to a real Access-Request while the Go Policy API is
wedged.

`docs/rules/radius.md` names this test and says what it is for:

> There is a `lab/` test that SIGSTOPs the Go process and asserts the defined
> behaviour — **it is the test that proves this architecture was worth choosing.**

The `rlm_rest` design rests on a claim: putting policy in a Go process beside
FreeRADIUS does not make the network fail in an undefined way when that process
dies. This harness makes it happen.

```bash
go test ./lab/policy/ -v          # needs Docker; about 45 s after the first build
```

## Two more suites, and one assertion every stack makes

Two more tier-2 tests live here, both in the Makefile's `LAB_REQUIRED_TESTS`:

- **`TestRADIUSVerifiesTheCredential`** runs the Policy API over the real
  `internal/store` (`policystub -database-url`) and seeds the schema through the
  store: the right PAP password for an opted-in account is accepted; a wrong one,
  an argon2id-only account and a request with no `User-Password` are refused; an
  exhausted, in-use, expired or revoked voucher is refused; an unused one is
  accepted once, left `in-use` with `first_used_at` set, and refused the second
  time; two accounting starts get two distinct `acctuniqueid`s.
- **`TestPolicyQuestionEncoding`** sends User-Names carrying `"`, `\`, C0
  controls, ESC, DEL, a trailing newline, a non-UTF-8 byte and the spliced
  `x","user_name":"<valid voucher>"}` to a fail-closed AND a fail-open stack: all
  are refused, and none reaches the failure branch.

And `startLabOn` reads `/proc/1/status` of every FreeRADIUS container it
starts and fails if any of the four uids is 0: radiusd does not run as root.

## Why SIGSTOP and not SIGKILL

A killed process's socket is closed by the kernel, so the connection is refused in
microseconds and FreeRADIUS finds out immediately. That is the easy case and it is
not the one that happens.

A **stopped** process still holds its listening socket. The kernel completes the TCP
handshake into the accept backlog and nothing ever answers. That is what a wedged
goroutine, an exhausted connection pool, a stop-the-world pause and a swapping host
all look like from FreeRADIUS — and it is the case where `rest`'s timeout, the
FreeRADIUS worker it is blocking, and the site's declared failure branch all matter
at once.

## What the harness is

One isolated stack per run, built from the repository:

| | |
|---|---|
| PostgreSQL | its own container, its own network, a generated password. The generated virtual server includes `sql`, `read_clients = yes` reads the client table before the first packet, and `rlm_sql` instantiates its pool at startup — so a stack without a database does not start at all |
| The RADIUS client | **a row in `nas`**, inserted by the harness before FreeRADIUS starts, with a secret generated per run. Not a line in `clients.conf`: `docs/rules/radius.md` requires that adding an access point be a plain database write, because regenerate-and-restart drops every in-flight EAP conversation and the in-memory TLS session cache on the site |
| FreeRADIUS | built from `lab/Dockerfile.freeradius`, with a raddb **generated by `internal/raddb`** into a temporary directory |
| Policy API | `lab/policy/policystub`, the real `internal/aaa` engine and handler over a fixture store, running on the host as a separate OS process so that there is something to signal |

`nas.secret` is the one declared cleartext copy of a shared secret in the schema —
FreeRADIUS validates `Message-Authenticator` itself and cannot use an encrypted one
— and `docs/rules/database.md` records that exception. This harness uses it; it
does not create a second one. The generated tree contains no shared secret at all.

It never touches `lab/docker-compose.yml`. That stack has fixed container names and
published ports and may be in use; a test that can only run when nothing else is
running is a test that does not run.

The configuration is **generated, not written here**. A hand-written raddb in this
directory would be a second source of truth for the thing under test: the day the
generator's failure branch changes, this harness has to follow it, and the only way
it can is by being the generator's output.

## What it cannot do

It drives `radclient`, so **it does not speak EAP**. The 802.1X case here is an
Access-Request carrying an `EAP-Message` attribute — enough to exercise the
classification and the failure branch, and not a supplicant. Proving the fail-closed
rule for a real EAP *conversation* needs `eapol_test`, which `internal/raddb` already
has for EAP-TLS; the two are complementary rather than one substituting for the other.

It also says nothing about a **full** `rlm_rest` pool. One request cannot exhaust
one, so the Status-Server assertion here is the weak form of the claim in
`docs/rules/security.md` §2. The strong form needs a load generator.

## Measured

Run against a freshly generated raddb on FreeRADIUS 3.2.10. The harness checks the
version of each candidate image, prints the one it got, and skips a stale tag rather
than running on it: a cached `foyer-lab-freeradius:policy-harness` tag can hold an
image built from an older Dockerfile, and an alpine-based image is FreeRADIUS 3.0.27 —
a different major dialect from the 3.2.x unlang the generator emits. A version pin in
a Dockerfile is advisory while a cached tag can stand in for it.

### A fail-closed site

| | |
|---|---|
| Baseline: valid voucher | Access-Accept, 0.10 s |
| Baseline: revoked voucher | Access-Reject, 1.09 s |
| Baseline: EAP-shaped request answered | Access-Reject, 0.08 s |
| **802.1X, Policy API SIGSTOPped** | **Access-Reject** — the fail-closed rule, demonstrated rather than asserted |
| Guest, Policy API SIGSTOPped | **Access-Reject** — the site's declared mode is fail-closed |
| Latency of the degraded answer | **5.09 – 5.18 s** across seven runs |
| Status-Server, Policy API SIGSTOPped | **Access-Accept** — the health check does not die with the thing it checks |
| Recovery after SIGCONT | immediate, first request |

### A fail-open site (`TestSIGSTOPAtAFailOpenSite`)

A site's failure mode is resolved when the tree is *generated*, so two failure modes
are two trees and two servers; this test starts a second stack.

| | |
|---|---|
| Guest at a **fail-open** site, Policy API SIGSTOPped | **Access-Accept**, `Class = Foyer:degraded`, `Session-Timeout = 600` |
| **802.1X** at that same fail-open site | **Access-Reject** — the operator's choice does not reach it |
| Degraded *accept* latency | **2.09 s**, against 5.1 s for the degraded *reject*: `reject_delay = 1` and the retry do not apply on the accept path |
| Recovery after SIGCONT | the site stops marking grants degraded, first request |

Giving the fail-closed harness fail-open advice turns exactly one assertion red —
`a_guest_at_a_fail-closed_site_is_rejected` — while
`802.1X_is_fail-closed_and_it_is_not_the_operator's_to_change` stays green. That pair
is what shows the guest half is configurable without taking the 802.1X half with it.

`Class` is an **octets** attribute (RFC 2865 §5.25), so radclient prints it as hex
(`Class = 0x466f7965723a6465677261646564`). `carriesDegradedClass` accepts either
rendering and derives the hex from `aaa.DegradedClass`; a plain string search would
pass the "healthy accept is not degraded" baseline whether or not the mark was there.

### The degraded answer is past the NAS retransmit interval

**The degraded reject takes 5.1–5.2 s, past the ~3 s NAS retransmit interval.** It
is inside the ceiling at which a NAS gives up, so a client sees a refusal rather than
a timeout. But every degraded authentication costs the server two or three requests
instead of one, and the `rlm_rest` pool that is already blocked pays for them.

The time is `rest`'s `timeout` (its 4 s default) plus `reject_delay = 1`;
`connect_timeout` is 0.5. `reject_delay` is a deliberate anti-brute-force control,
not slack — reducing it trades a security property for a latency number.

## Building an Access-Request: never `EAP-Message` with `User-Password`

RFC 3579 §3.1 forbids an Access-Request from carrying both `EAP-Message` and
`User-Password`, and FreeRADIUS refuses such a packet at the socket, before any
virtual server runs:

```
Receive - Bad packet from host 127.0.0.1: Packet contains
EAP-Message and non-EAP authentication attribute
```

So there is no reply and **no line in radiusd's trace even at `-xx`**, which reads
like strong evidence about the configuration and is not: "no line in the trace" says
the packet did not reach the configuration. Every measurement here passes through
`authRequest`, so a bug in how the harness builds a packet is indistinguishable from a
bug in the subject. The EAP-shaped baseline guards that precondition, and its failure
message says to suspect the packet first.

## The client this harness registers

The generated tree contains no shared secret and no static client
([`docs/rules/security.md`](../../docs/rules/security.md) §7: no default RADIUS shared
secret, ever). Without a client, a packet from an unknown source address is
**silently discarded** — and a discard is not an Access-Accept, so every
`Access-Reject while the Policy API is stopped` assertion would pass vacuously. The
wiring baseline fails first in that case and says so.

Three rules anyone extending the harness should follow:

1. **Seed the `nas` row before FreeRADIUS starts.** `read_clients = yes` loads the
   table once at startup; a row added later is found by the dynamic-clients virtual
   server instead, which works but is a different code path.
2. **`nasname` is the address the packet actually arrives from.** `radclient` runs
   inside the FreeRADIUS container here, so `127.0.0.1` is right.
3. **Never rotate the secret mid-test** on a client the server loaded at startup.
   The running server keeps the old one and drops the packet with *"invalid
   Message-Authenticator! (Shared secret is incorrect.)"* — which looks exactly like
   a SIGSTOP symptom while having nothing to do with one.

## What `internal/raddb` generates for the failure branch

The generated `authorize` section reads `rest { ... every rcode given an action ... }`
followed by `if (ok || updated) / elsif (fail) / else`, with the fail branch stating in
place what it does. The explicit action list matters: `rlm_rest` maps the Policy
API's HTTP 403 to `userlock`, whose default action in `authorize` is to return
immediately, so without it the deny branches would never run.

1. **The per-site advice is carried.** `internal/aaa.Advice` is the resolved,
   renderable form: `Dot1X`, `Guest`, `GraceSeconds`, `GraceAttributes`. A
   fail-open accept emits `Session-Timeout` (bounded, capped at an hour),
   `Acct-Interim-Interval` and `Class = Foyer:degraded` — and nothing else,
   because everything else would have been looked up and the lookup is what is
   unavailable. `raddb.Config.GuestFailureAdvice` carries it.

   **`Advice` is resolved at generate time, never at request time** — by the time
   the failure branch runs, the thing that would resolve a rule is the thing that is
   down. `SiteFailurePolicy.Advice()` produces one value per site;
   `aaa.FailurePolicies` returns all of them, and says whether the answer came from
   configuration or from the default.

2. **802.1X is classified inside that branch, on EAP presence.** `if (&EAP-Message)`
   → reject, unconditionally, whatever the site is configured for. It is asserted in
   `internal/raddb` against the generated unlang and in this harness against a real
   server.

3. **The Policy API is sent the fields it reads.** The two identities travel as
   `user_name_hex` / `outer_user_name_hex` (`%{hex:&Attr}`), because jsonquote
   rewrites bytes >= 0x80 on the amd64 build; `eap_message` is a presence marker,
   never the blob. Two client fields travel beside them, and neither is the
   NAS-supplied `nas_identifier`, which is attacker-chosen:
   - `radius_client` is `%{client:shortname}`, the name of the row FreeRADIUS looked
     up — the server's answer rather than the packet's claim;
   - `client_ip` is the packet's source address, the key FreeRADIUS matched the
     client by on a packet verified with that client's secret. **A voucher's site is
     resolved from `client_ip`**, because a name is not unique across venues and an
     address is what FreeRADIUS matched.

### Per-site routing, and the trap that keeps it unbuilt

Different advice for different sites would render as **one virtual server per
distinct `Advice` value** (not per site), with each client routed by the `nas`
projection's `server` column, which FreeRADIUS maps to a client's `virtual_server`.
That mechanism was measured and works:

```
rlm_sql (sql): Adding client 127.0.0.1 (labclient) to SERVERCOL clients list
No 'listen' section in virtual server SERVERCOL. Adding client to global client list
...
Reply-Message = "SERVER-FROM-SQL-COLUMN"
```

It is the only supply that survives an outage: `read_clients = yes` means clients
come from SQL, `rlm_sql` reads exactly six columns, and the sixth is `server`.

**And it has a trap:**

```
$ radiusd -XC        # nas.server names a virtual server the tree does not have
rlm_sql (sql): Adding client 127.0.0.1 (labclient) to DOES_NOT_EXIST clients list
Cannot add client - virtual server DOES_NOT_EXIST does not exist
Configuration appears to be OK          <-- gate 1 passes
$ radclient ...
(0) No reply from server for ID 82
```

A `nas.server` value with no matching generated server **silently drops the
client**: the server comes up, reports OK, and every packet from that NAS goes
unanswered. No blue/green gate sees it, because the gates probe with the harness's
own client. The two writers — `internal/raddb` (generates the tree, restart-class)
and `internal/store`'s `nassync` (writes `nas.server`, sql-only) — run in different
processes with no ordering guarantee.

**So routing is not built.** The advice set must **collapse to one value**, rendered
into `default`, where every client already lands. A set that does not collapse is
refused **by name at Validate**, before the blue/green apply writes a byte:

```
raddb: the sites do not agree on a failure model:
  [dot1x=fail-closed guest=fail-closed grace=300] for site(s) s2;
  [dot1x=fail-closed guest=fail-open grace=600] for site(s) s1.
  Routing a client to a per-advice virtual server is the mechanism for this and it
  is not built ...
```

`nassync` carries `server` through its diff, insert and update paths and pins it to
`""`. Populating it requires an ordering invariant between the two writers.

### Where this diverges from the field, and why

**Nobody in this industry ships per-site fail-open in the RADIUS policy.**
PacketFence makes its decision in `post-auth`, branching on an attribute rather than
the module rcode, sets no action overrides, and so returns before its own condition
runs — `rad_postauth()` turns `RLM_MODULE_FAIL` into an Access-Reject. Its `:-Allow`
default looks like fail-open and is not: it covers an API that answered without the
attribute, never one that did not answer. PacketFence buys availability with a
Galera cluster. authentik's RADIUS outpost rejects on every error path with no flag.
ClearPass's degraded mode is a read-only local replica that keeps answering.
daloRADIUS is not in the request path. Cisco ISE is the only per-scope knob and it is
per policy *rule*, about an unreachable identity store rather than an unreachable
control plane.

**The industry's real answer lives on the NAS**: Cisco's Inaccessible
Authentication Bypass (`authentication event server dead action authorize vlan N`)
and Aruba's `critical-role` / `cached-critical-role`. The case that matters most is
the RADIUS server being unreachable, and a server that is unreachable cannot express
a policy at all.

Foyer diverges deliberately and narrowly. **What this covers is the failure mode
Foyer's own architecture creates** — the Go control plane down while FreeRADIUS is
up and answering — and nothing wider. A NAS that cannot reach Foyer at all is
answered by critical-VLAN on the NAS or not at all, and this setting must never be
described as though it covered that. It is worth having because in hospitality and
retail a lobby of guests who cannot connect is the loss, while in enterprise NAC —
PacketFence's centre of gravity — closed is right. That is a difference in
deployment, not a disagreement about the protocol — which is why the setting is per
site rather than per install, and why 802.1X is excluded from it whatever the site
says.

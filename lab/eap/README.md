# `lab/eap` — the `eapol_test` suite

Real EAP conversations against the configuration `internal/raddb` generates, on a
real FreeRADIUS 3.2.10.

```bash
go test ./lab/eap/ -v                      # needs Docker; about 30 s once an image is cached
FOYER_POLICYSTUB=$(go build -o /tmp/ps ./lab/policy/policystub && echo /tmp/ps) \
  go test ./lab/eap/ -v                    # skip the in-test compile on a busy machine
```

`docs/rules/testing.md` says why this exists:

> `radclient` and `radtest` **do not speak EAP**. A project whose entire
> architectural rationale is "EAP is too hard to implement ourselves" cannot have
> zero EAP coverage in CI.

and what its scope is:

> Every EAP method Foyer claims to support has an `eapol_test` case, and the claim
> is removed if the case is removed.

## What is claimed, and what has a case

| Method | Case here | Standing |
|---|---|---|
| **EAP-TLS** | `eap-tls completes for an authorized identity` | **MEASURED**, passes |
| EAP-TTLS/PAP | none | planned; not generated — [`docs/rules/security.md`](../../docs/rules/security.md) §1 |
| PEAP-MSCHAPv2 | none | not generated — [`docs/rules/security.md`](../../docs/rules/security.md) §1 |

`TestOnlyClaimedMethodsCanBeGenerated` is the mechanical half of *"the claim is
removed if the case is removed"*: it drives `raddb.Generator` at six EAP types and
requires each to be refused, so somebody cannot add a method to the emitter and
forget to add a case here. It needs no Docker and runs in the ordinary suite.

## Why blue/green gate 3 and not gate 1 or gate 2

Measured on 3.2.10, and it is the sharpest argument for the whole `eapol_test`
requirement:

| Tree | `radiusd -XC` | Second server on an alternate port | An EAP conversation |
|---|---|---|---|
| `ttls { virtual_server = "does-not-exist" }` | **exit 0**, echoes the name back | **starts, answers Status-Server** | `No such virtual server` |

Gate 1 cannot see it because the item parses. **Gate 2 cannot see it either**,
because Status-Server never enters the `eap` module. Only this file can.

## What the harness is

One isolated stack per run, all of it thrown away afterwards:

| | |
|---|---|
| PostgreSQL | its own container, its own network, a generated password. `read_clients = yes` reads the client table before the first packet, so a stack without a database does not start |
| The RADIUS client | **a row in `nas`**, inserted before FreeRADIUS starts, with a secret generated per run. `nas.secret` is the schema's one declared cleartext copy of a shared secret; this uses that exception rather than creating a second |
| FreeRADIUS | a cached 3.2.x image, **checked for its version** — see below |
| The configuration | **generated by `internal/raddb`**, never written here |
| Certificates | issued in the container at test time. Nothing is committed and no image carries a CA |
| Policy API | `lab/policy/policystub` — the real `internal/aaa` engine over the same fixtures the SIGSTOP harness uses |

The certificate **Common Names are the policy engine's own identities** —
`LAB-VOUCHER-OK` and `LAB-VOUCHER-REVOKED`. That is the point rather than a
shortcut: an EAP-TLS supplicant's authorization answer then comes from the same
code that answers for a voucher, and a stub written here would have been a second
source of truth for what "allowed" means.

It never touches `lab/docker-compose.yml`. That stack has fixed container names and
published ports and is not this harness's to touch.

## What this suite guards against

Each of these is a property of FreeRADIUS 3.2.x that a generated tree can get wrong,
and each has a case:

- **An EAP request must reach the policy engine.** `eap { ok = return; updated =
  return }` returns from `authorize` before `rest`, so a tree written that way never
  asks about an EAP request and accepts every certificate the configured CA signed.
  `a certificate the CA signed is not by itself authorization` fails against such a
  tree.
- **The outer identity is chosen by the supplicant, on EAP-TLS too.** A supplicant can
  present the certificate for one account while sending the `User-Name` of another
  real account. Authorization keys on the inner identity
  ([`docs/rules/security.md`](../../docs/rules/security.md) §8 is not only a PEAP/TTLS
  concern).
- **`radpostauth` must not record the outer name**, or every 802.1X row an operator
  reads is an audit record the supplicant wrote.
- **An Access-Reject must carry no EAP-Success and no MS-MPPE keys.** A reject built
  from an accepted reply carries both: the supplicant reports success for a session
  the NAS refuses, and keying material travels in a packet that must carry none.
- **The FreeRADIUS image must be the right major version.** A cached image tag can
  be FreeRADIUS 3.0.27 — a different dialect — and still pass much of a suite. Both
  harnesses check the version they got and print it.

Two harness behaviours keep it honest:

- **`docker run` on an absent tag tries to pull, and a daemon whose registry path
  is unreachable hangs there without erroring.** The probe loop that picks an image
  therefore calls `docker image inspect` first and never `docker run` on a tag that
  is not present locally.
- **`go build` from inside a test is a second compiler beside the one that started
  it**, which can exhaust a busy machine. `FOYER_POLICYSTUB` names an already-built
  binary.

## What this cannot do

The same limit `lab/policy/README.md` states: **it prevents regressions in what is
already known, and it cannot teach what hardware does.** `eapol_test` is a
conformant supplicant. A Windows machine, an iPhone and a Cisco access point are
not, and tier 4 is a device matrix for that reason.

Specifically unmeasured here: certificate enrolment on any real client, what a
supplicant does with an Access-Reject that carries no `EAP-Message` (measured only
that `eapol_test` reports `FAILURE`), and every TLS version negotiation a real
supplicant might attempt.

# internal/api — CONTRACT

The admin and portal HTTP surface, generated from `web/contract/openapi.yaml`.

## Invariants

1. **The contract is the source, and the server interface is build output.**
   `internal/api/gen/server.gen.go` is generated by `make generate` and is never
   hand-edited — the same standing `raddb/` has. `Server` asserts
   `var _ gen.StrictServerInterface = (*Server)(nil)`, so an operation added to
   the contract and not implemented here **fails the build**, and a handler with
   no operation has no method to satisfy. `make generate-check` fails when
   regenerating produces a diff.

2. **Base path is `/api/v0`**, on the stdlib `http.ServeMux` — not `/api/v1`.

3. **Deny by default.** Every operation is gated on the `x-permission` the
   contract declares for it, read from the embedded document at construction.
   An operation with no annotation makes `api.New` **refuse to start**; an
   operationId with no gate entry is refused at request time. There is no path
   through `Server.gate` that reaches a handler without either a session or an
   operation the contract itself marks `security: []`.
   - `401` `/problems/not-signed-in` when there is no session.
   - `403` `/problems/forbidden`, with `params.required`, when the session's
     role may not do this.
   - **One exception, and the contract states it:** `signOut` answers `204`
     whether or not there was a session, because a client that has just been
     told `401` by something else must still be able to reach it.

4. **Session cookie: `__Host-foyer_admin_session`** — Secure, HttpOnly,
   SameSite=Lax, `Path=/`, no `Domain`. The bearer token is stored hashed; the
   CSRF token is stored in the clear because `getAuthSession` has to hand it back
   to a client that cannot read the cookie.

   The name is not restated in Go any more than it has to be: a client generated
   from `securitySchemes.sessionCookie` must read the cookie this server writes, so
   `TestSessionCookieNameIsTheContractsName` reads it out of the embedded document
   and compares it with `sessionCookieName`, and the two cannot part company from
   either side.

5. **CSRF on every state-changing operation outside the `portal` tag, and on every
   download**, in `X-Foyer-CSRF`, compared in constant time. The requirement is
   **derived from the contract** — method, the `text/csv` answer that makes a GET a
   download (the exports: they write `data-exported` and hand personal data out, and
   a `SameSite=Lax` cookie rides a cross-site top-level GET), tag, and whether the
   operation declares `security: []` — never from a list in Go, because the contract
   says the rule "cannot vary by operation" and a copied list is a second place for it
   to disagree with itself. Wherever the token is required, a request the browser
   marks `Sec-Fetch-Site: cross-site` or `same-site` is refused too (OWASP's fetch
   metadata check; the guest portal is the console's same site).

6. **No CORS.** The console is same-origin; the contract's `servers:` entry says
   so. There is no CORS middleware at all rather than a narrowed one.

7. **Nothing echoes a submitted credential** — not in a response, not in an
   audit entry, not in an error string. `asAPIError` funnels every unrecognised
   error into `/problems/internal` carrying no text, so a store error cannot
   reach a client. `docs/rules/security.md` §9: no stack traces, no internal paths.

8. **The store is behind ports.** `ports.go` declares one narrow interface per
   aggregate; nothing in this package imports `internal/store`. Ports speak the
   contract's own generated types, because the contract *is* the domain model
   here and a parallel Go model of every schema would be one more place for each to
   drift.

9. **A shared secret is returned exactly once.** `createNas` and
   `rotateNasSecret` are the only responses in the contract that carry one, and
   there is deliberately no port method that reads one back. **Both** of them must
   be rendered by a client: a console that shows registration's secret and discards
   the identical value rotation produces leaves every access point on a driver that
   cannot push a secret permanently unable to authenticate, with no operator able
   to configure it. See §9.1.

   **9.1 The write-only property, and what the field does instead.** A value is
   disclosed by the write that created it and by no other call, ever. Held by
   `internal/api/secretwriteonly_test.go` in two forms, because one is not enough:
   the behavioural walk drives **every GET in the contract** with two real server-
   issued secrets and asserts neither appears in any response, *and* asserts how
   many of those reads actually reached a handler — a walk that quietly degrades
   into `422` refusals cannot disprove a leak. The structural test walks every
   response schema in the contract, descending through `allOf`/`anyOf`/`oneOf`, and
   requires the property to appear on exactly two.

   **Each half closes a specific way to miss a leak.** A contract test that did not
   descend into `allOf` would pass a `sharedSecret` added to `getNas` inside one. A
   walk that did not count its `422`s would pass a rotated secret leaking out of
   `ListNas`, because many of its reads would never reach a handler.

   **The field disagrees, and the disagreement is recorded rather than argued
   away.** Across PacketFence, authentik, Microsoft NPS, Cisco IOS/IOS-XE,
   OmniAccess, OpenWISP and Ubiquiti's own documentation: **no product surveyed
   uses write-only semantics for a RADIUS shared secret, and none has a rotation
   action at all.** authentik says so in a source comment — *"Shared secret is not
   a write-only field, as an admin might have to view it"* — and enforces
   readability by `change` permission rather than by withholding it. PacketFence's
   published OpenAPI spec contains zero `writeOnly` markers; OpenWISP renders the
   client secret in cleartext in its admin list.

   What the two products that actually **generate** a secret agree on is the half
   this package acts on: both show it at the moment of change, and NPS tells the
   operator to save it for configuration on the NAS. **So the reveal is the field's
   pattern and the write-only property is Foyer's own stricter choice** — kept,
   because it is stated in the console's copy and because a portal whose API is
   published, open source and Apache-2.0 should not hand a stored RADIUS credential
   to any caller who can reach a device row. The cost of that choice is that the
   value must leave the building on the screen that shows it, or it is gone, and
   the console's acknowledgement exists to pay it.

   **Rotation on a device the driver cannot push is allowed, warned about, and
   refused only where there is no route back** (`409`, driver cannot push *and* the
   device is unreachable — the value could then be entered only by hand by nobody).
   The field is silent on this rather than permissive: a RADIUS shared secret is
   half of a pair, so a platform that rotates one and cannot program the far end has
   bricked that device, and no surveyed product offers rotation for that reason. The
   console's answer is the one the reveal makes true — make the value obtainable,
   state the price before the operator commits, and refuse only where the price
   cannot be paid.

10. **Audit on state change, and never under an approximate kind.** `AuditKind`
    is a closed enum; an action with no member of it is left unrecorded rather
    than filed under a near-enough one. `record` is best-effort: the action has
    already happened, and failing the response would tell an operator their
    change did not land when it did.

    **Except for an irreversible change, which is recorded fail-closed.**
    `eraseDataSubject` and `updateRetentionPolicy` build their entry with
    `auditEntry` and hand it to the port, which writes it in the change's own
    transaction: an entry that cannot be written means the change is not made
    (`/problems/internal`). An export writes its entry before a byte leaves (15d).
    A new operation that cannot be undone takes one of those two shapes; `record` is
    for the ones that can.

    `updateController` writes `controller-updated` — it can replace a stored
    credential, which is the most security-relevant change this surface makes — and
    `discoverFromController` writes `controller-discovery-run`, whose subject is the
    **controller** and whose params carry the counts. `nas-registered` would be the
    near-enough value for the second and wrong twice over: one entry for what may be
    nine adoptions, and a device named as the subject of a change made to a
    controller.

    **The amendment's entry names fields and never values.** `apiKey` and
    `password` are write-only in this contract, and a log read months later by
    somebody who was not there is the last place either may reappear. There is a
    test on that specific string.

    **A failed guest authorization is the case where this rule holds and the answer
    is somewhere else entirely.** A controller refusing after the `303` is on the
    wire has no `AuditKind`, and adding one would be wrong for a reason stronger than
    approximation: `AuditEntry` **requires** `actorId` and `actorUsername`, and the
    actor is a guest with a voucher. There is no operator, so the entry could only be
    written by inventing one.

    The surface for it is `listAuthAttempts` with `AuthSource: driver` and
    `AuthEventKind: authorize-failed`. It is written by `internal/portal`'s
    `Authorizations` port, from inside the closure this package hands to the response
    writer, because the grant and the placement are the service's and reassembling
    them at the writer would be a second copy of what it already holds. See
    `internal/portal/CONTRACT.md` invariant 10.

    **`createSite` is recorded as `site-created`.** `nas-registered` is the
    near-enough value this rule exists to refuse — it names a *device* as the subject
    of a change that made a *venue*. This is the operation every installation
    performs first, so without it the log that records every later change to a venue
    would say nothing about where the venue came from.

    **A kind nothing emits is the same defect one step along**, which is why the
    member and the write exist together and why `TestCreateSiteIsRecorded` reads the
    entry back through `listAudit` rather than asserting on the port.

    **Whether an entry names a venue follows from its kind, and `auditScopes` is
    where the per-kind decisions live.** Without it every entry would be built
    without a `siteId` — `site-created` included — so `audit_log.site_id` would be
    uniformly NULL and the contract's *"null for a change that is not a site's"* would
    describe nothing. A nullable
    column with no rule beside it is the shape `docs/rules/database.md` names.

    Three things about it are load-bearing:

    - **It is per kind, not per call site.** Somebody reading a log written months
      ago has the kind and nothing else, so the kind has to be what says how to read
      the value. `recordIn` consults the table rather than trusting its caller: a
      site passed for a deployment-wide kind is **dropped**, which is what makes a
      null on `operator-created` mean only what the contract says it means.
    - **Both directions are checked against the contract's own enum.** A new
      `AuditKind` with no decision fails `TestEveryAuditKindDeclaresItsScope`, and a
      table where every kind answered the same way fails
      `TestBothAuditScopesAreUsed`.
    - **`listAudit` takes no `siteId`**, and that is not an omission. The console's
      audit screen says so in as many words: a good half of the entries have no
      venue, so filtering by the header's switcher would hide exactly the rows an
      administrator opens the screen for. The member is a **column**. What the
      scope makes usable is `store.AuditFilter.SiteID`, over the column migration
      `00003` added and the `(site_id, at DESC)` index over it.

    **`operator-password-changed` is in the enum and this package does not yet write
    it** — `changeOwnPassword` records nothing, while `web/mock` records it. That is a
    known gap, separate from the scoping rule above.

    Adding an `AuditKind` is a **four-package change**: the enum in `web/contract`,
    a row in `web/fixtures` so the screen's copy is one somebody has looked at, an
    entry in the console's `Record<AuditKind, …>` catalogue — a **compile error**
    until it has one — and the write here.

11. **A figure the contract declares is read from the contract, never copied.**
    `portalBudgets` is not three constants in this package: all three are read out
    of the embedded document (`gen.GetSpecJSON`) — `x-max-decoded-bytes` on
    `HeroImageUpload.dataBase64` and on `PortalSettingsUpdate.logoDataUri`,
    `x-budget-bytes` on `PortalSettings.budgets.codeBudgetBytes` — and it **panics**
    rather than falling back if a declaration is missing, naming the hop that was
    absent. The specification is compiled into this binary, so its absence is a
    build fault, and a default would be the copy again wearing a different hat.

    A copy goes wrong in either direction: an image ceiling here that disagrees with
    the one in `web/contract/src/index.ts`, with nothing comparing them; or a logo
    ceiling that binds a console and no server, so a `logoDataUri` past its
    512 000 B ceiling — which is already ten times the whole 51 200 B portal
    document budget, inside the document, paid on every launch — is answered
    `200 OK` and stored. `docs/rules/database.md` — derive the
    stand-in from what it stands in for.

    **And the figures are reported, not just applied.** `withBudgets` attaches all
    three to every `PortalSettings` this package answers, so no adapter stores a
    byte count and no console has to keep its own.
    `TestPortalSettingsReportsTheBudgetsItEnforces` drives an upload at each
    *reported* figure plus one and requires a refusal: the number shown and the
    number applied are one number, and a second copy on either side turns it red
    from whichever side moved.

12. **A field the store cannot hold is refused here, not by PostgreSQL.**
    `createNas` refuses a blank `ipAddress` as `required` and an unparseable one as
    `not-an-ip-address`, with the same two parses `internal/apistore` performs
    before writing the row — a validator that admits what the writer rejects has
    moved the `500` rather than removed it. `NasCreate` makes the field optional,
    `radius_clients.address` is `inet NOT NULL`, and FreeRADIUS matches a packet to a
    client by its source address and nothing else.

12a. **`createNas` refuses `driver: coa` that names no `coaVendor`**, as `required`
    on that field. `coa` is the one member of `NasDriverKind` that names a *family*
    rather than a vendor: Cisco identifies a session by a `Cisco-AVPair
    audit-session-id` VSA and Aruba by `Calling-Station-Id` in its own spelling, and
    RFC 5176 §2.3 makes the NAS match on **every** session-identification attribute
    in the request — so the wrong dialect matches nothing. A careful device answers
    `Error-Cause 503`; a careless one **ignores the request and acknowledges it**,
    which `docs/rules/testing.md` names as the one CoA failure a lab cannot
    reproduce. There is no safe default, so this asks.

    It is not `required` in the schema because it is required for one of five
    drivers; `DRIVER_SHAPES[driver].coaVendor` is the single table that says which,
    read by this handler, by `web/mock`, and by the console's form. **`web/mock` does
    not validate requests**, so the refusal is hand-written there too, exactly as
    `ipAddress`'s is.

    This is the first of two gates and it cannot be the only one: it stops a *new*
    row being made, and `apistore.ErrCoAVendorUnknown` covers every row it cannot
    reach.

13. **`too-large` sends its figures where the contract says they go.** `bytes` and
    `limitBytes` travel in `params.fieldParams[field]` as well as at the top level:
    `x-fault-params` declares that the fault needs them and names the per-field
    location, because a refusal can mark several fields at once. Sending only the
    top-level copy is the *"At least 0."* mistake one field along.

14. **An operator on a temporary password may do exactly three things.** While
    `MustChangePassword` (`operators.must_change_password`) is true, the gate answers
    `/problems/password-change-required` (403) to every operation but
    `GetAuthSession`, `SignOut` and `ChangeOwnPassword` (and the public
    `GetAdminSetup`, which says nothing about the caller). The flag's only writer is
    `foyerctl create-operator --must-change-password`, the host-side way to hand
    somebody a temporary password; `changeOwnPassword` clears it and refuses the
    current password as the new one (`unchanged`).

    **In the gate, not in a client.** A console that only *routes* to the
    change-password screen has forced nothing: a second browser, a stale tab or `curl`
    with the session cookie walks straight past it. `web/mock` carries the identical
    rule, and `temporary_password_test.go` drives the wire. Reads are refused too.

    There is no shipped password: the install carries no credential, and invariant 15
    is how the first administrator is made.

15. **Foyer ships no credential; the first administrator comes from a one-time
    setup** (`handlers_setup.go`). `getAdminSetup` answers `required` from the
    `ConsoleSetup` port; `completeAdminSetup` answers `409 /problems/setup-complete`
    whenever no setup is open — **before** it reads the body, so a finished install
    tells a caller nothing more — and otherwise validates (`setupCode`, `username`,
    `password` at `passwordMinimum`), then hands the code to
    `ConsoleSetup.CompleteSetup`, which compares it and creates the administrator and
    closes the setup **in one transaction** (`ErrSetupClosed` for the loser of a race,
    `ErrSetupCodeWrong` → `422 incorrect`, `ErrConflict` → `duplicate` on
    `username`). On success it signs the browser in exactly as `signIn` does
    (`startSession`) and records `operator-created` with the new administrator as the
    actor and `params.setup: true`. A wrong code is logged without the code. The
    throttle is the console's **per-address** bucket only (invariant 23); a nil port
    is an install with no setup, `required: false` and `409`. The survey and why a
    code rather than a first-come page are in the file's header.

15a. **An install with no administrator is never offered the sign-in form.**
    `getAdminSetup` carries a second bit, `noAdministrator`: with the setup closed it
    asks `ConsoleSetup.HasAdministrator` and reports the absence. Without it both
    `false` cases are one answer, and a bootstrap that never ran — an interrupted
    installer, a restore that lost `console_setup`, a container started without
    `foyerctl open-setup` — is rendered by the console as a sign-in form that can
    never succeed, over copy promising a recovery needing an administrator this
    install does not have. **The bit is not a way in:** it is asked only when the
    setup is closed, the screen it selects opens no form, and `completeAdminSetup`
    answers `409 setup-complete` in exactly that state.

15b. **The portal page design is validated here, whole, and narrowed before any
    guest reads it.** `updatePortalSettings` applies five rules beyond the schema in
    order — `duplicate`, `link-before-sign-in`, `required`, `not-a-link`,
    `ends-before-start` — first failure wins, on the one key `design`. The two link
    rules apply only to **visible** blocks: a hidden block is a draft, and a
    template's "Review us" button starts hidden and empty. The link allowlist is
    `internal/portal.IsLink`, the function the renderer re-checks with, not a copy.
    A design in the patch **replaces** the stored one. Every read answers a
    design, never null.
    `getPortalContext` and the server-rendered documents both call `narrowDesign`
    with the site's local date (`Config.Now` in the site's time zone,
    `getSiteTimeZone`): hidden blocks and blocks
    outside their dates are **not in the response**, because a pre-authentication
    read that merely did not render them would still publish them.

15c. **The portal's two entries say what changed, and write nothing when nothing
    did** (`audit_portal.go`). `portal-settings-changed` and `portal-terms-changed`
    record `{"changed": {field: {"from": …, "to": …}}}`, the same shape
    `network-settings-changed` and `maintenance-settings-changed` record. An
    append-only entry cannot be edited and a wrong one is corrected by a later one,
    so a row that cannot name what moved cannot be corrected either. Three things
    follow, and all three are load-bearing:
    - **The difference, not the request.** `updatePortalSettings` is a PATCH whose
      body is pointers where nil means "not supplied", and the console sends the
      whole form. The entries are built from the settings **before** the write
      against the settings **after** it, and an empty difference writes no entry.
      Deciding from which pointers were non-nil would record a change to every field
      the console holds on every save, including the save an operator makes after
      reading a form and pressing the button. The before side is a copy taken
      before the call, so a store that amends in place cannot rewrite it.
    - **A value over `auditValueMax` (200 bytes) is a length and a digest, not
      the value.** `terms.summary` is legal text a venue may withdraw and a
      `logoDataUri` is up to 512 000 B, and a copy in a log that never deletes one is
      a copy nobody can edit. The same posture `internal/redact` takes with a
      guest's MAC and `foyer_audit_pseudonymise` takes with an identifier. A
      short value is echoed whole, because a digest does not tell a reader what the
      name changed from.
    - **The design is a roster, not the page.** `design` is reduced to its blocks
      — id, kind, placement, visibility, in the order shown — plus the accent and
      the headline, and the block text is not in it. A bare block count cannot tell
      an operator which block went, which is the question the page builder's log
      exists to answer, and a whole layout would be a copy plus text the log's only
      `UPDATE` path would then redact. The roster is bounded by
      `PortalDesign.Blocks` and is deliberately **not** put through the cap.

15d. **An export is bounded, recorded before it is sent, and never a
    complete-looking file with rows missing** (`handlers_reports.go`).

    - **Bounded.** `from` and `to` are required; an inverted range is
      `range-inverted` and one past the operation's `x-max-range-days` is
      `range-too-long` with `maxDays` in `fieldParams.to`. There is no "everything".
    - **Recorded first, fail-closed.** The `data-exported` entry is appended before
      the first row exists, and if the append fails the export is refused `500`.
      This is one place invariant 10's best-effort rule is inverted, and the
      reason is the same rule read honestly: there the change has already happened,
      here nothing has left yet. An `Audit` port that is not wired refuses the
      export as `501` rather than sending it unrecorded.
    - **Streamed, and failure is visible.** `csvStream` writes the status on the
      first byte that is actually ready. A failure before it returns the problem
      document with its real status; a failure after it aborts the connection
      (`http.ErrAbortHandler`), so a client sees a failed download rather than a
      short file. The write deadline moves forward per chunk instead of the admin
      listener's 30-second whole-response bound.
    - **The columns are the contract's.** `readReports` binds each export's
      `x-csv-columns` to the cell functions here and **refuses to start** on a
      column either side lacks. The embedded document carries Go-cased operation
      ids (`ExportSessions`), which is what the lookups key on.
    - **`reports:export` is administrators only**, and it is a permission rather
      than `sessions:read` because a bulk offline copy is a different act from a
      page on screen. `getTrends` is `authenticated`: it names nobody.
    The fourth export — marketing consent — is one more `dataset[T]` and one more
    operation beside these three, and it is **not** a column on `exportGuests`: the
    contract says why. Its rows come from `GuestDataStore`, not `ReportReader`,
    because a consent is that port's record.

15e. **Marketing consent is a ticked box and nothing else**
    (`handlers_guestdata.go`). `readGuestForm` records a consent only when the venue
    is asking, `marketingConsent` is exactly `yes`, a `consentVersion` came with it,
    and a phone number or an e-mail address was given; the port then refuses a
    version the venue never published (`ErrUnknownConsentVersion`). Accepting the
    terms is never read as consent — `acceptTerms` runs the same reader as the
    other two forms. **Consent is never the price of the network**: nothing about
    it refuses a sign-in. A required detail left blank or malformed is answered
    `303` to the form with `details-required` / `details-invalid` **before**
    anything is claimed, and never with the value. The portal form fields carry no
    schema constraint on purpose — a contract refusal would be a `422` JSON body in
    a CNA — so the handler owns every bound. `withdrawOwnMarketingConsent` answers
    the same `303` whether or not anything was withdrawn, and withdraws only for a
    session **bound to a grant** — never for one merely confirmed by
    `VerifyPresence` now: presence proves the MAC is online, not that the caller is
    its owner, so accepting it would let any portal user withdraw an online guest's
    consent. The phone branch's copy of the consent rule (`withVerifiedPhone`) is
    held by `TestAPhoneGuestWhoDoesNotTickTheBoxLeavesNoMarketingRecord`. The admin
    withdrawal is audited `marketing-consent-withdrawn` naming the consent by id.

15f. **`disconnectSession` refuses before it withdraws, and withdraws before it asks
    the device.** The order is the invariant:
    `SessionByID` → `ended` is `409 session-not-live` → `Devices.CanEndSession`
    (the **driver's** answer) is `409 disconnect-unsupported` → the voucher and
    the grant the operator ticked, through `Guests` and `Vouchers` → `EndSession` →
    one `session-disconnected` audit entry. A refusal changes nothing and writes no
    entry; an attempt writes one whether or not the device confirmed, because a
    voucher that went is a change. The device's failure is a `200` carrying
    `session-end-failed` with `cause` (`refused` + `errorCause`, `no-answer`,
    `bad-secret`, `error`) — never the error's text. `radacct` is not written:
    the device's Acct-Stop closes the row. Held by `internal/api/disconnect_test.go`
    and, against PostgreSQL and a UDP fake NAS, `internal/apistore/disconnect_test.go`.

    **The permission is `sessions:manage`, held by both roles.** The one split this
    contract has that neither role withholds — a permission named *read* must never
    reach a control that throws a device off the network. `OperatorPermission` in the
    contract carries the reasoning and the survey (ClearPass Guest, UniFi's hotspot
    operator).

    **`revokeVoucher: true` also needs `vouchers:manage`**, checked in the handler
    before anything is read: it is the `revokeVoucher` operation's act, and the gate
    reads only this operation's `x-permission`, so without the check an option would
    be the way round another operation's permission. `403`
    `params.required: vouchers:manage`. Both roles hold both today; the check is
    what keeps a role added later from inheriting the bypass. Held by
    `internal/api/disconnect_permission_test.go`.

## The two surfaces

16. **One contract, two listeners.** `docs/rules/security.md` §7 puts the admin
    console and the guest portal on separate listeners, and the contract covers
    both, so the split happens here: `Handler()` serves the console's operations
    and `PortalHandler()` serves the operations tagged `portal`.

    The split is **derived from the contract's own tag**, never from a list in Go,
    the same derivation `csrfApplies` uses. An operation asked for on the wrong
    surface answers `404` — on that listener there is no such route — and
    deliberately not `403`, which would say the route exists and you may not have
    it.

    `TestTheGuestSurfaceIsExactlyThePortalTag` checks the direction that matters:
    no operation requiring a permission may appear on the guest surface, because
    that listener is bound wide and reachable before authentication.

    **Middleware order is load-bearing.** `oapi-codegen` wraps in slice order, so
    the last entry is outermost. The slice therefore reads innermost-first:
    `[guestSession, gate, onSurface]` gives `onSurface → gate → guestSession →
    handler`. Written in reading order it puts the surface check inside the gate,
    and `listNas` on the guest listener answers `401` rather than `404`.

17. **The guest surface carries a session the console must never see.**
    `guestSession` resolves the browser-to-MAC binding through
    `portal.Service.Resolve` and is mounted on `PortalHandler` only. The contract's
    portal operations declare **no parameters at all**, so there is no operation
    through which a MAC can arrive: it arrives once, from the NAS, on the redirect
    that brought the guest here, and is bound server-side from then on.

18. **The authenticating operations answer `303 See Other` on every
    outcome**, with `Cache-Control: no-store` and **no body**. The iOS Captive
    Network Assistant re-checks captivity only after a document navigation;
    without one its button stays *Cancel*, and Cancel disassociates the device.

    The contract declares no `403` with a problem document for `acceptTerms`'s
    presence failure: a form navigation answered `403 application/problem+json`
    renders raw JSON to a guest with no client left to turn it into a sentence, and
    it is not a navigation the CNA treats as a re-check — so the one response that
    could explain the failure would also be the one that throws the guest off the
    network. The `404` for a method the venue does not offer stays, because no guest
    navigation reaches it: the button is hidden.

19. **The NAS is asked to authorize after the response is written.**
    `portalRedirect` writes the redirect, flushes it, and only then runs the
    closure `portal.Service` handed it, under `context.WithoutCancel` so a client
    that hangs up does not abort the grant. Android destroys the login WebView the
    instant the network validates, so anything written after that may never be
    seen.

    **Its error is dropped here and reported inside the closure.** Returning it would
    hand a non-nil error from `Visit…` to `ResponseErrorHandlerFunc`, which would
    write a problem document over a response already written — a superfluous
    `WriteHeader` and a corrupt body. The reporting therefore lives inside the
    closure: `portal.Service.deliver` retries what is worth retrying and records the
    outcome, which writes both the operator's `authorize-failed` event and the
    grant's `Delivery`. The guest's next `getPortalStatus` answers `not-on-network`
    rather than `connected`.

    The `303` and its `Location` are **unchanged by the failure**, and must be. The
    guest is mid-flow; a response the CNA does not treat as a captivity re-check
    leaves its button reading *Cancel*, which disassociates the device.

20. **`getPortalContext` answers `200` when the controller cannot be reached.**
    The contract enumerates what its `403` means — not associated, wrong AP or
    site, already authorized — and an outage is in none of them. Nothing is
    granted: the authenticating operations run the same check, fail closed
    on the same verdict, and tell the guest `generic` rather than `not-present`.

21. **A deployment that declares more than one replica is refused unless its
    pre-authentication rate limiter is shared.** `Config.ControlPlaneReplicas`
    reaches `portal.NewService`, which will not construct against an in-process
    `Limiter` above one replica: N processes grant N times the configured rate with
    nothing saying so. Zero and one mean what they say, which is what v1 ships.

## What a caller can make this process spend

22. **No body is read past its ceiling, and the ceiling is applied before anything
    reads.** `limitBody` (`hardening.go`) refuses a declared `Content-Length` over
    the ceiling unread and wraps every other body in `http.MaxBytesReader`; the
    request validator, the generated decoders and the form parser all map the
    resulting error to the contract's `PayloadTooLarge` (`/problems/too-large` on
    `body`, with `bytes` and `limitBytes`). 16 KiB on the portal surface, 1 MiB on
    the console, and `putPortalHeroImage` alone gets a ceiling **derived from**
    `HeroImageUpload.dataBase64`'s `x-max-decoded-bytes`. `cmd/foyer` puts a
    listener-wide `http.MaxBytesHandler` in front of both muxes as well.
    `TestAStreamedBodyStopsAtTheCeiling` counts the bytes the server consumed.

    **The console's figures are for a signed-in caller.** A request with no session,
    and every request to a public operation (`signIn`), is held to
    `AnonymousBodyLimit` — 16 KiB, the portal's figure — on every operation. The
    validator decodes a body into a tree before the gate runs, and the tree is
    30–40× the text for a body of small values (measured: one anonymous 1 MiB
    `[0,0,…]` to `createAccount` peaked at ~40 MiB of heap, fifty at once at
    1.3 GiB), so a byte ceiling an anonymous caller could reach at a megabyte would
    not be a memory ceiling. `TestAnAnonymousCallerGetsTheAnonymousCeiling` and
    `TestEveryOperationWithABodyRefusesAnOversizedOne` pin it.

    **An account's bucket key is a digest of the normalised username**, never the
    text: the username has no `maxLength`, and a key as long as the body held for a
    refill period would make the limiter's key bound a bound in keys and not in bytes.

    **Bodies over the anonymous ceiling share one in-flight budget** (`bodybudget.go`,
    not a setting): only a signed-in caller can send one, and it waits in
    arrival order for room rather than being refused, so an upload beside another
    takes turns instead of failing with a status the contract does not declare.
    Every other body — anonymous, the portal's, a signed-in caller's ordinary one —
    draws on a second budget, so the decoded memory of a synchronised anonymous
    flood is bounded too (`TestAnonymousBodiesShareABudgetToo`).

    **Both budgets are decoded bytes sized from the memory plan, and every body is
    weighed at its real size** (`memplan.go`). From `Config.Memory`
    (`cmd/foyer/memory.go`'s soft limit and argon2id bytes): a tenth of the soft
    limit for the process, the rest after argon2id for bodies — at most 8 MiB small,
    the remainder large (94 MiB in the shipped container). `limitBody` reserves
    `decodeWorstPerByte` × length capped at the budget; the validator weighs the read
    body (`bodyWeight`: 13 B per byte, 64 B per JSON value), hands back the excess,
    and **refuses `413` a body heavier than its whole budget** — no body runs alone
    past its budget. **No ceiling can be set above what its budget decodes**:
    `networkBounds` offers the plan's maxima (console 7 MiB shipped, never above
    16 MiB; portal and anonymous 128 KiB), a write above is `422`, and a stored value
    is clamped on read. `TestTheShippedPlanHoldsTheContractsLargestBody`,
    `TestTheConsoleCannotSetACeilingTheContainerCannotHold`, `TestABodyIsWeighedAtItsRealSize`.
    `TestLargeSignedInBodiesTakeTurns`. `cmd/foyer` bounds concurrent connections
    per listener (`connlimit.go`), which is the other half of the same memory bound.

    **The HTTP middleware list is innermost-first.** The generated wrapper applies
    `handler = middleware(handler)` in slice order, so the last entry is outermost;
    reading it the other way round puts the validator outside the security headers.
    `limitBody` must be outside the validator.

23. **`signIn` and `loginWithAccount` are throttled per client address and per
    account before any password is checked.** Two token buckets
    (`internal/ratelimit`), and an attempt must fit in both. The console answers
    `429` `/problems/rate-limited` with `Retry-After` and `params.retryAfterSeconds`
    (the contract's `SignInRateLimited`); the portal keeps its `303`-always rule and
    sends the guest back to the form with `e=generic`. The answer is identical for
    names that exist and names that do not. The client address is the socket's peer,
    never a header.

    **The console's per-account bucket is split by trusted device**
    (`devicecookie.go`, OWASP's device-cookie defence). A successful `signIn` (or
    setup) sets `__Host-foyer_device`
    (`v2.<key id>.<account digest>.<nonce>.<mac>`), HMAC-signed under the ring
    `Ports.DeviceKeys` holds; an attempt carrying a valid one for that username
    spends from that device's own bucket (`adminDevice`, the same `consoleAccount`
    policy), every other attempt from the account's shared bucket. A success clears
    **only the bucket it spent**, so the account holder signing in does not refund a
    stranger. `TestAStrangerCannotLockTheOwnerOutOfTheirAccount`.

    **The ring survives a restart**: persisted sealed under FOYER_KEK
    (`device_cookie_keys`, migration 00053), the newest key signing, rotated after
    `deviceKeyRotateAfter` (90 days) and never by a restart, a retired key verifying
    for `deviceCookieLifetime` after its successor. The ring is cached for an hour.
    A nil port keeps a per-process key; a failed read keeps the last ring, and with
    none issues and trusts nothing. `TestATrustedDeviceSurvivesARestart`,
    `TestTheDeviceKeyRotatesOnPolicyAndARetiredKeyStillVerifies`, and over
    PostgreSQL `internal/apistore` `TestATrustedDeviceSurvivesARestartOverPostgres`.

    **The portal's account bucket is keyed by account and source address**:
    Apple's CNA destroys its cookies with the sheet, so a device cookie would leave
    most guests in the shared bucket; the socket's peer is what no CNA drops.
    `TestAStrangerCannotLockAGuestOutOfTheirPortalAccount`. A NATed guest network
    degenerates to one bucket per account.
    `completeAdminSetup` spends the address bucket only.

## What is not implemented, and why

**Nothing, unconditionally.** `notImplementedOperations` is empty and a test pins
that in both directions, so a name cannot quietly join it.

An operation whose **port is nil** still answers `501` with a problem document,
which is the honest gap: not configured, rather than not built. `501` rather than
something plausible is the whole point — a handler that returns convincing
hardcoded JSON without touching a database is indistinguishable, to a caller, from
one that works.

**The guest portal is all of it or none of it.** `Config.Portal` is refused at
construction if some of its ports are wired and others are not: a grant store
with no driver seam is a portal that records grants for devices nothing
confirmed, and there is no useful subset.

## `NewServer`

`NewServer(any)` returns a server with **no ports wired**, so every operation that
needs one answers `501`. It exists for tests that need a server and no store;
`cmd/foyer` builds its server with `api.New` over the ports `internal/apistore`
supplies.

## Phone sign-in

Four operations: `requestPhoneCode` and `verifyPhoneCode` on the guest surface (form
navigations, `303` on every outcome, `404` where the venue does not show the button), and
`getPhoneSignIn` / `updatePhoneSignIn` behind `portal:read` / `portal:manage`.

- **The provider's keys are write-only.** `gen.PhoneSignIn` has no field a key could
  arrive in; `credentialsSet` is a bool. The audit entry says whether the keys changed,
  never what they are.
- **The per-address limit keys on `RemoteAddr` only** (`clientIP`), put in the context by
  `guestSession`. An `X-Forwarded-For` is a header the guest writes.
- **`phone` cannot be offered before a provider is configured**
  (`updatePortalSettings`, `needs-phone-provider`).

## The network tag

Every setting an operator needs is configurable from the console, so these live in
the contract. Eleven operations (`handlers_network.go`): the portal's address,
throttles and ceilings; the portal certificate; FreeRADIUS's generator settings,
EAP-TLS certificate, client-table sync and apply; per-device CoA timing. Reads
`nas:read`, writes `nas:manage`, every write audited (`network-settings-changed`,
`portal-certificate-changed`, `radius-clients-synced`,
`radius-configuration-applied`, all deployment-wide).

- **A write takes effect without a restart.** Every write is followed by
  `ReloadNetwork`, which reads the store back and swaps the whole
  `EffectiveNetwork` in one atomic store; the throttles are reshaped in place
  (`ratelimit.Limiter.SetPolicy`, no refund), the body ceilings are read per request
  (`bodyLimitFor`, `LimitBody`), the header ceiling is enforced per request below
  `MaxHeaderCeiling` (`LimitHeaders`), and the `NetworkRuntime` (`cmd/foyer`) is told
  the new set.
- **A value saved here wins over the deployment's** (`NetworkBootstrap`), and every
  answer says which is in force (`source`).
- **No answer carries a private key.** An upload is checked
  (`config.ParseCertificatePair`, `CheckPortalPair`) before it is handed to the
  store to seal; the answer says `keySet: true`. No KEK is `501`.
- **Every bound is checked here, with its figure** (`below-minimum` /
  `above-maximum`), and reported in `bounds`; the schema carries none, so the
  refusal always has the number.
- **Every editable figure is sent with its own range and its own default** — the
  console's `Advanced` section states both and offers a reset.
  `NetworkSettings.defaults` is `DefaultThrottles()` / `DefaultBodyCeilings()`
  member by member, because `bounds.throttleBurst.default` is one figure for four
  buckets that ship differently; `listCoaTiming` sends `bounds` from the same
  constants `updateNasCoaTiming` validates against. **The range sent is the range
  enforced**: `settingbounds_test.go` holds one past each stated end refused and
  each end itself accepted.
- **A RADIUS-client write syncs the client table**: `createNas`, `updateNas`,
  `deleteNas`, `rotateNasSecret` and `discoverFromController` call
  `syncAfterClientWrite`, whose outcome never fails the write.

## Setting bounds read from the contract

`contractRange` (`contractbounds.go`) reads a property's `minimum`/`maximum` from
the embedded contract, once. `PhoneAbuseControls.bounds` (`PhoneAbuseLimitsUpdate`'s
ranges, `otp.DefaultLimits`' defaults) and `PhoneSpendCap.bounds`
(`PhoneSpendCapUpdate.dailyLimit`) are built from it, so the range the console states
and the range request validation refuses on are **one number read from one
document**. It panics on a property that has lost a bound — a contract edit that
the handler tests fail on at once. The store returns the controls without bounds;
the handler attaches them (`withAbuseBounds`, `withSpendCapBounds`).

## Portal authorizations

Two operations (`handlers_portalgrants.go`, port `PortalGrantStore`):
`listPortalGrants` (`sessions:read`) and `disconnectPortalGrant` (`sessions:manage`).

- **A grant is ended on its controller, in `disconnectSession`'s order**: refusals
  that change nothing (the option's own permission, 404, `session-not-live`,
  `disconnect-unsupported`), then the voucher and the grant, then the controller,
  then the audit (`session-disconnected`, subject `portal-grant`).
- **A body option's own permission is checked by its handler**, and
  `TestBodyOptionPermissionsMatchTheContract` ties every property-level
  `x-permission` in the contract to one; `web/mock` enforces them generically.
- **FreeRADIUS apply answers are the supervisor's** (`RadiusApply.detail`); see
  `internal/raddb` `Handoff`.

## Messaging settings

Seven operations: `getSiteTimeZone` / `updateSiteTimeZone`, `getPhoneAbuseControls` /
`updatePhoneAbuseControls`, `getPhoneSpendCap` / `updatePhoneSpendCap` and
`sendPhoneTestMessage`, reads behind `portal:read` and writes behind `portal:manage`
(administrators only). Every write is audited: `site-time-zone-changed` (the venue's),
`phone-spend-cap-changed` (the deployment's, `siteId` null) and `portal-settings-changed`
with `section` for the limits and the test message.

- **Every daily boundary is the site's calendar.** `siteLocation` / `siteToday` read the
  `TimeZones` port per request (the store-backed one caches 30 s and forgets on write);
  trends buckets, a portal block's dates, `sentToday` and `vouchersRedeemedToday` all use
  it. A port that cannot answer falls back to the server's clock.
- **A zone is validated against this process's zone database** (`LoadTimeZone`); `Local`
  and the empty name are refused `not-a-time-zone`.
- **`getSiteTimeZone.updatedAt` is when the zone changed**, null until an operator changes
  it; storing the zone a site already has does not move it. Both worlds and `web/mock`
  answer the same (`sites.time_zone_changed_at`, migration 00044).
- **The abuse limits are bounded by the schema and never off.** The handler adds the one
  cross-field rule (`perNumberPerDay >= perNumberPerHour`, `below-minimum` with
  `minimumCount`). `PhoneSignIn.limits` reports the limits in force at the venue, so the
  two panels cannot disagree.
- **The test message's answer and entry name the outcome, never the number or a key.**
- **Phone sign-in meets guest data: `verifyPhoneCode` reads the venue's guest-data
  setting** before the code is spent, less the `phone` field; a refused form returns to
  the code form (`sent=1`) with the code unspent. The verified number fills `phone` where
  the venue collects it and is the consent's contact (`withVerifiedPhone`).

- **The FreeRADIUS worker ceiling is PostgreSQL's connection budget.**
  Every worker is an rlm_sql connection (the generator sizes the pool at the worker
  count), so `updateRadiusServerSettings` bounds `maxServers` at
  `RadiusMaxServersCeiling` = `max_connections` 80 − 3 superuser-reserved − the
  control plane's pool 25 − reaper and retention 2 + 2 − two `foyerctl` runs 2 × 2 =
  **44**; a larger bound would let FreeRADIUS open more connections than
  PostgreSQL accepts.
  `TestTheWorkerCeilingFitsThePostgresBudget` reads `deploy/compose.yaml`; `web/mock`
  answers the same bound. A row stored above it is generated at the ceiling
  (`apistore.generatorSettings`).
